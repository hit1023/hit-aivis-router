# 待ち行列（キュー）の設計メモ

個人環境なので軽めの設計。方針は「呼び出し側を壊さず、足りないところだけ足す」。

## 困りごと

- `/speak` は同期（MP3 がそのまま返る）。台ごとの**同時実行数の制限が無い**ので、
  同時に来た分が全部エンジンへ届く。非力な台（CPU のみのサーバーなど）は、同時に2本来ると
  両方がタイムアウトすることがある（実測は未了）。
- 1モデル1台の方針（`home_for`）で、同じ話者の合成は同じ台に集まる。集まる分だけ詰まりやすい。

## 方針

`/speak` を「受付だけ返して後で結果を取りに来る」非同期（202＋ポーリング）には**しない**。
自作アプリ（音声アシスタント等）や webui が全部「POST して MP3 を受け取る」前提だから。

### Phase 1（実装済み・既定は無効）: 台ごとの同時実行の上限

- `BACKEND_CONCURRENCY`（既定 `0` = 制限なし = 従来どおり）。1以上にすると、台ごとに
  その数だけ同時に合成し、超えた分はルーターの中で先着順に待つ。
- `BACKEND_QUEUE_TIMEOUT`（既定 60 秒）。待ちすぎたら **503 + `Retry-After: 5`**。
  台の不調とは扱わない（退避しない・別の台で再試行もしない。待っているのは混雑のせいだから）。
- `/backends/status` の各台に `inflight`（合成中）と `waiting`（順番待ち）を出す。
- 実装は `app/backend_pool.py` の `Backend.synthesize_mp3`（`asyncio.Semaphore`。先着順）。
- 台の選び方（`pick` / `home_for` / sticky）は変えない。`/speak_stream` は文を順に送るので影響なし。
- デスクトップ版は台が1つで既定 `0` のまま。影響なし。

メモリ上だけで完結するので、再起動すると待ち行列は消える（待っている呼び出しは接続ごと切れる）。
音声合成は数秒で終わり、呼び出し側が自分で再試行できるので、これで十分と判断。

### 使い始めるとき

1. CPU のみのサーバーで、同時 1 / 2 / 3 本を流して成功率と所要時間を測る（`hit-aivis-queue-lab` の考え方を流用）。
2. 台がすべて同じ性能とは限らないので、まず全台共通の値で運用する。
   足りなければ台ごとの値（`backends.json`）に広げる（Phase 1.5）。
3. `docker-compose.yml` / `.env` に `BACKEND_CONCURRENCY=1`（または 2）を足して `docker compose up -d`
   （`restart` では環境変数が反映されない）。戻すときは `0`。

### Phase 2（必要になったら）: Redis + arq の非同期ジョブ

「長文を一気に読み上げ」「複数台のルーターから 1 つのキューを共有」が必要になったときだけ。
`POST /speak_jobs` → `job_id` → `GET /speak_jobs/{id}`。`/speak` とは別口にして既存の呼び出し側は触らない。
Redis が増える運用コストがあるので、必要が出るまで入れない。学習用の実験は `hit-aivis-queue-lab`。

### zenoh との関係

zenoh の pub/sub は「進捗を知らせる」用途で、仕事の取り合い（キュー）には使わない。
台ごとの `inflight` / `waiting` を `aivis/backend/**` に流して画面で見る、という使い方なら相性がよい（未実装）。

## ロールバック

`BACKEND_CONCURRENCY` を `0` に戻して `docker compose up -d`。コードの既定が `0` なので、設定しなければ何も変わらない。
